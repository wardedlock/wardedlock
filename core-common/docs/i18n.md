# 🌐 Internationalization (i18n)

Wardedlock uses a centralized i18n system for localizing error messages and API responses. To ensure compatibility across all environments, we use a **Native-to-ASCII** encoding strategy.

## 🏗️ How it Works

The system relies on Spring's `MessageSource` and a custom Gradle convention plugin to handle translation files.

### 1. Location
Translation files are located in:
`core-common/src/main/resources/i18n/`
- `errors_en.properties`: The source of truth for all keys (English).
- `errors_vi.properties`: Vietnamese translations (ASCII escaped).

### 2. The Code Connection
- **Keys**: Defined via `ErrorCode.getMessageKey()` (e.g., `error.validation_failed`).
- **Resolution**: `ErrorEnvelopeFactory` injects `MessageSource` and resolves the key based on the `Accept-Language` header provided by the client.

## 🛡️ Encoding Convention (Native-to-ASCII)

Java `.properties` files expect ISO-8859-1 by default. To support special characters (like Vietnamese diacritics) without encoding issues:
1.  **English** files remain as plain text.
2.  **Non-English** files are converted into ASCII using `\uXXXX` escapes.

### 🛠️ Developer Workflow

If you add or edit a translation in `errors_vi.properties`, you might see a CI failure if you commit raw UTF-8 characters. Follow this workflow:

1. **Edit the file** using your preferred editor (it's okay to type raw characters).
2. **Run the fix task**:
   ```bash
   npm run i18n:fix
   # OR
   ./gradlew :core-common:nativeToAscii
   ```
3. **Verify**: The task will convert characters like `à` to `\u00e0`.
4. **Commit**: Add the converted file to your commit.

## 🔍 Validation
The project includes a `nativeToAsciiCheck` task that is wired into the standard `./gradlew check` lifecycle. This ensures that no non-ASCII characters ever reach the main branch.
